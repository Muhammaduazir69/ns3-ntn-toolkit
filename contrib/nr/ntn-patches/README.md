# Vendored 5G-LENA (nr) provenance and NTN patch series

## What this module is

`contrib/nr` is **upstream 5G-LENA `nr` v3.3.1** (the latest release of the
`5g-lena-v3.3.y` line, 15 Oct 2024) carried on the toolkit's **ns-3.43** base,
with **seventeen** local adaptation patches applied on top. Nothing else in
the tree diverges from pristine upstream v3.3.1: a full-tree content diff of
`model/` and `helper/` against pristine v3.3.1 reports only the files of the
patches below, and no removed files; patch 16 adds `model/nr-mac-phr-ce.{h,cc}`
(listed in `CMakeLists.txt`, which the patch also touches).

v3.3.y is the newest 5G-LENA line that targets an ns-3.42/3.43-class base;
therefore the vendored module already tracks the latest upstream release that
is compatible with this toolkit's ns-3 base. See
`5G_LENA_UPGRADE_ASSESSMENT_2026-07-18.md` (repo root) for why v4.0 (ns-3.44)
and v5.0 (ns-3.48, the only line with native NTN) are ns-3-base migrations
rather than in-place `nr` bumps.

## Upgrading later

When the toolkit's ns-3 base moves to 3.44 (→ nr v4.0) or 3.48 (→ nr v5.0,
native NTN), drop in the pristine upstream `nr` for that base and re-apply
whichever of these patches upstream has not itself fixed. Patches 03/04
(PDCP Control-PDU handling) are the ones most likely still required, since they
reflect a modelling scope choice, not an ns-3-version quirk.

## Not implemented: Msg4 contention resolution (TS 38.321 5.1.5)

Checked in Wave 7A; not feasible as a local patch on nr v3.3, for these reasons:

1. There is never anything to resolve. `NrGnbMac::ProcessRaPreambles` treats two or
   more identical preambles in one occasion as a collision in which none is detected
   (no RAR is sent, every colliding UE times out and retries). No two UEs can therefore
   ever hold the same temporary C-RNTI, which is the situation Msg4 contention resolution
   exists for. A capture (strongest preamble detected) model at the gNB PRACH would be
   needed first.
2. `NrUeMac::RecvRaResponse` declares random access successful on the RAR itself and
   promotes the temporary C-RNTI (its own comment: "in principle we should wait for
   contention resolution, but ... no one is received"), so there is no state in which a
   ra-ContentionResolutionTimer could run.
3. Msg3 and Msg4 are RRC messages carried by `NrRrcProtocolIdeal` by default (and
   `NtnRealStackHelper` keeps the ideal protocol), so the 48-bit CCCH SDU that the UE
   Contention Resolution Identity MAC CE echoes is not a MAC payload. `NrMacHeaderFsDl`
   defines LCID 62 (UE_CONTENTION_RESOLUTION) but nothing builds or parses that CE.

Doing it properly needs a PRACH detection model with capture, the real RRC protocol
(SRB0 over RLC TM), the CE in the gNB MAC Msg4, and a UE timer started after Msg3 and,
for NTN (Rel-17), extended by the UE-gNB RTT. That is the scope of the nr v5.0 / ns-3.48
migration rather than a local patch.
